# Бизнес-требования: Система управления выездным обслуживанием «FieldOps»

## 1. Контекст и проблематика
Наша компания оказывает услуги по ремонту и обслуживанию промышленного оборудования на объектах заказчиков. В штате есть диспетчеры (офис) и сервисные инженеры (выездные специалисты). 
Сейчас заявки распределяются через мессенджеры и таблицы, из-за чего инженеры часто получают противоречивые задачи, а руководство не видит реального местоположения сотрудников и статуса выполнения работ. Отчеты о выполненных работах сдаются на бумаге.

## 2. Цель
Создать прототип корпоративной системы, которая автоматизирует процесс создания заявок, назначения их на инженеров, отслеживания перемещения инженеров по городу и сбора отчетов о проделанной работе с мобильных устройств.

## 3. Функциональные требования

### 3.1. Роли пользователей
*   **Диспетчер (Web-интерфейс)**: создает заявки, назначает инженеров, отслеживает их статус и местоположение на карте, просматривает отчеты.
*   **Сервисный инженер (Мобильное приложение)**: получает назначенные заявки, принимает или отклоняет их, меняет статус (В пути, В работе, Завершено), отправляет фотоотчет, транслирует свою геопозицию.
*   **Администратор системы (Web-интерфейс)**: управляет справочниками (пользователи, оборудование, объекты).

### 3.2. Web-интерфейс для Диспетчера (Angular)
*   **Дашборд**: список активных заявок с фильтрацией по статусу, приоритету и инженеру.
*   **Карта**: отображение текущего местоположения всех активных инженеров и объектов (точек, куда нужно прибыть).
*   **Создание заявки**: указание объекта (адрес, координаты), описания проблемы, приоритета и выбор инженера.
*   **История**: просмотр архива заявок и прикрепленных к ним фотоотчетов.

### 3.3. Мобильное приложение для Инженера (Kotlin)
*   **Авторизация** и получение push-уведомлений о новых заявках.
*   **Список задач**: новые, в работе, завершенные.
*   **Экран заявки**: детали, адрес, кнопка «Построить маршрут» (интеграция с mock-картами).
*   **Управление статусом**: смена статуса заявки (Принята -> В пути -> В работе -> Завершена).
*   **Фотоотчет**: возможность сделать фото через камеру и прикрепить к заявке.
*   **Фоновая геолокация**: приложение каждые 5 минут отправляет координаты устройства на backend (через mock или реальные GPS-данные).

### 3.4. Backend и API (C# / ASP.NET Core)
*   Аутентификация и авторизация (JWT, роли).
*   REST API для работы с заявками, пользователями и геоданными.
*   Генерация событий (Kafka) при смене статуса заявки (например, `TaskStatusChanged`, `EngineerLocationUpdated`).
*   Обработка загруженных фотографий (сохранение в локальное файловое хранилище или S3-совместимое хранилище).

## 4. Нефункциональные требования
*   **Технологический стек**: 
    *   Mobile: Kotlin (Android)
    *   Web: Angular (TypeScript)
    *   Backend: C# / .NET (ASP.NET Core)
    *   Database: PostgreSQL (с расширением PostGIS для работы с геоданными)
    *   Message Broker: Kafka (или mock)
    *   Инфраструктура: Docker, Docker Compose
*   **Безопасность**: пароли хешируются, API защищено JWT токенами.
*   **Производительность**: время отклика API не более 500 мс при стандартной нагрузке.

## 5. Модель данных (основные сущности)
*   `User` (id, role, name, email, phone, current_lat, current_lon)
*   `Task` (id, status, priority, description, client_name, address, lat, lon, assigned_user_id, created_at, updated_at)
*   `PhotoReport` (id, task_id, photo_url, created_at)
*   `TaskStatusHistory` (id, task_id, old_status, new_status, changed_at)

## 7. Демонстрационный сценарий (для проверки работы пайплайна)
1. Диспетчер заходит в Web-интерфейс и создает новую заявку: «Сломался станок, ул. Ленина, д. 10».
2. Диспетчер назначает заявку на инженера Ивана.
3. В мобильном приложении Ивана появляется уведомление. Иван принимает заявку.
4. Иван меняет статус на «В пути». На карте у Диспетчера точка Ивана начинает двигаться к адресу (можно эмулировать сменой координат через API).
5. Иван приезжает (статус «В работе»), чинит станок, делает фото и меняет статус на «Завершено».
6. Диспетчер видит изменение статуса в реальном времени (через WebSockets или поллинг) и открывает фотоотчет в Web-интерфейсе.
7. В логах GitLab CI/CD отображаются успешные проверки безопасности (SAST/SCA) и пройденные тесты.

## 8. Источники данных и интеграции
*   **Геоданные**: использование открытых карт (например, Leaflet или Yandex Maps API mock).
*   **Kafka**: если реализуется, то события должны быть строго типизированы (JSON Schema).
*   **База данных**: начальные тестовые данные (seeders) должны включать 2-х диспетчеров, 5 инженеров и 10 тестовых заявок.
